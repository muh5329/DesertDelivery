Lesson 01 · Desert Delivery

From key to motion

You press W and the bike accelerates. Five modules sit between those two facts. Learn where they are and you can put your hands on almost any feature in the game — because nearly everything the courier does enters through this one path.

~10 minutes reading ~25 minutes at the keyboard New words: 2 Assumes: you can already write GDScript

Your mission says you want to expand this codebase by hand. That means the first thing you need is not a theory of software design — it is a map. Somewhere to put your hands. This lesson gives you one path through the code, learned properly, and one small feature you add yourself at the end.

We start here because the control path is the spine. A new vehicle, a new button, a new thing the courier can do — almost all of it lands somewhere on this line.

Two words, and only two

You will meet a lot of design vocabulary eventually. Today you need exactly two, because without them the rest of the lesson has to keep gesturing.

Interface
Everything a caller must know to use a piece of code correctly. Not just the function signature — also the order you must call things in, what happens when it fails, and what it quietly assumes. If you have to know it to use the thing, it is part of the interface, whether or not it is written down. In this repo: GroundDrive's interface is "set intent and mods, then call step(delta)". That ordering is part of it. Nothing in the type system says so.
Seam
A place where you can change behaviour without editing in that place. The classic example is a function that takes its dependency as an argument: you can hand it a different one and the function never changes. In this repo: Controls.Source is a seam. The bike's physics cannot tell whether the intent came from your keyboard or from the autopilot, which is exactly why the test suites can drive the real bike.
Why this matters for hand-coding

A seam is where you are allowed to add something without disturbing what is already working. When you know where the seams are, "where do I put this?" stops being a guess. That is the whole trick.

The chain

Read this top to bottom. The right-hand column in grey is the important half — what each module is not allowed to know. Those exclusions are what keep the path straight.

InputMap
Godot's own table: the key W is the action accelerate. Knows nothing about this game. Edited in the editor, not in code.
Controls.Keyboard
Reads every action once a tick and produces a Controls.Reading — axes, look, and which actions fired. Must not know what a wing, a cargo rack or a delivery is. It reports what you did, never what it meant.
a Scheme
Turns that Reading into a Controls.Intent: decides that brake means braking on the ground and pitch in the air. Owned by the thing being controlled — Controls.Foot for the boy, Bike.BikeScheme, Truck.TruckScheme. This is where meaning lives.
Rider
Holds the intent for one tick. Handles the commands that change state — mount, dismount, wings, reset — then hands the rest down. The only module that reads a raw Intent. Everyone else asks it questions instead: courier(), is_stopped().
GroundDrive
Consumes the intent as physics: throttle, drag, slope, steering, wheel rays, landings. One tick in, one tick of motion out. Must not know about fuel, cargo or upgrades — those arrive pre-digested as mods, so the physics never learns about the economy.

Now read the real thing

Three short excerpts, verbatim from your repo. Read them against the chain above — you are looking for the handover points, not the details.

gameplay/controls/controls.gd — the device, and nothing but the device

	func read(scheme: Scheme, delta: float) -> Intent:
		var i := Intent.new()
		if blocked:
			_mouse_delta = Vector2.ZERO
			return i
		var r := _device(delta)
		i.run = r.run
		i.aim = r.aim
		# Two commands mean the same thing whatever you are sitting on.
		if r.just(&"interact"): i.press(INTERACT)
		if r.just(&"reset_bike"): i.press(RESET)
		if scheme: scheme.map(r, i)
		return i

That last line is the seam. Keyboard hands the Reading over and lets somebody else say what it meant.

entities/vehicles/vehicle.gd — the default meaning, for anything with wheels

class GroundScheme:
	extends Controls.Scheme
	var vehicle: Vehicle
	func map(r: Controls.Reading, i: Controls.Intent) -> void:
		i.steer = r.side
		i.throttle = r.forward
		i.brake = r.back
		i.boost = r.run
		i.handbrake = r.down(&"handbrake")
		if r.just(&"fire"): i.press(Controls.FIRE)

entities/player/rider.gd — one tick of routing

	var i := controls.read(_foot if is_on_foot() else vehicle.control_scheme(), delta)
	_last_intent = i
	if i.pressed(Controls.INTERACT):
		if is_riding(): request_dismount()
		else: request_mount()
	...
	if is_riding():
		...
		vehicle.apply(i)
The one line worth memorising

_foot if is_on_foot() else vehicle.control_scheme() — the Rider picks the Scheme each tick from whatever you are currently controlling. Everything about how the keys behave follows from that choice.

Check yourself

Your turn

You can already write GDScript, so none of this is a syntax exercise and I am not going to walk you through it line by line. The exercise is the path. Part A is the five-minute warm-up that proves you have it; Parts B and C are where the actual learning is, and neither of them is mostly typing.

Part A — give the vehicles a horn

A horn is the smallest real feature this game can have: one InputMap entry and three files, one line each. Put it in Vehicle.GroundScheme. Hold on to why there — Part B is about that choice.

  1. InputMap: add an action horn, bind it to H.
  2. gameplay/controls/controls.gd — declare the command constant.
  3. Same file — make _device() actually poll it.
    One trap here, and it is silentAn action missing from ACTIONS means r.just() returns false for it forever, with no error and no warning. If your horn does nothing later, suspect this first.
  4. entities/vehicles/vehicle.gd — press the command in GroundScheme.map(). Note r.just() versus r.down().
  5. entities/player/rider.gd — react in the is_riding() branch. message.emit(text, seconds) is already wired to the HUD by setup().
  6. Ride, press H. Then godot --headless --path . -- --test=feature_tests — it should still say PASS (0 failures).

Part B — now put it in the wrong place, on purpose

This is the part that teaches. There were three other places that horn could have gone, and every one of them would have compiled and "worked". Predict the behavioural difference for each before you touch anything — write the predictions down, then move your horn and find out.

  1. Into Keyboard.read(), beside INTERACT and RESET. What can you now honk from that you could not before? Is any of it wrong?
  2. Into Controls.Foot as well as GroundScheme. Same question, and a second one: what have you now duplicated, and what happens the day the horn needs a cooldown?
  3. Into Truck.TruckScheme only. Where does the horn work now? More interestingly — what did you have to know about GroundScheme to answer that?

Then move it back. The point is not that GroundScheme is the only defensible answer — it is that you can now say why it is the one you would defend, in terms of who is allowed to know what.

Part C — two predictions, no typing

Answer both from the code, before you test them. Both are more interesting than they look.

  1. Does your horn work while the truck's cargo rack is open? Read TruckScheme.map() and answer from the structure alone. Whatever you conclude, the reason is the valuable half — it is a property of how the two Schemes compose, and nobody wrote a line of code to make it true.
    Check yourself after you have committed to an answer In cargo mode TruckScheme.map() never reaches super.map(r, i). So every control GroundScheme owns — throttle, brake, steer, fire, and now your horn — is inert while packing, for free. Structure got you a feature you did not implement.
  2. Make the horn work on foot, but not while swimming. Don't write it yet — decide where the rule lives. Controls.Foot has no idea the boy is in water. The Rider knows the Mode. The Player body knows it is swimming. Three candidates, and the choice is a real design judgement rather than a syntax question. Pick one, justify it in a sentence, then build it if you want it.
    What I would ask myselfWhich of those three would still be right if you later added a fourth thing that suppresses the horn — say, sitting at a courier counter? Put the rule where the next rule like it would also go.

Bring me your Part B predictions and your Part C answer to #2. Where you chose to put that rule, and why, tells me far more about what to teach next than whether the horn honks.
